Evaluating answers with an LLM-as-judge

A separate language model scores each of your answers against five quality metrics. This page explains what those metrics are, why a second model is involved, and how to export the results for further analysis.

What this feature does

The application ships with a built-in evaluator based on the LLM-as-judge pattern: instead of trusting your own model to grade its own answers, you pick a second local model and ask that model to score each answer on five well-defined criteria. Each criterion comes back with a 1–5 rating and a written explanation.

This is useful in three situations in particular:

  • You want to know whether the answer actually came from the documents you uploaded, or whether the model slipped in something from its own training.
  • You are comparing two retrieval configurations — hybrid vs. dense-only, different chunk sizes, different embedding models — and want a quantitative signal that "answer quality went up."
  • You are teaching and want to demonstrate what good retrieval looks like by showing students the rubric an evaluator applies.
A signal, not ground truth

An LLM-as-judge is itself a language model and inherits the same caveats as the model that produced the answer. It is at its best catching obvious failures — an answer that ignored the documents, a citation to a nonexistent source, a response that never addresses the question. It is least reliable on subtle judgments where reasonable readers disagree. Treat scores as a relative signal across configurations, not as an absolute verdict.

The five metrics

Each metric is scored on a 1–5 scale. The judge is given the question, the retrieved context, and the answer; it returns a JSON verdict with steps, explanation, evaluation, and rating. Five metrics are run in a fixed order; together they cover the failure modes most worth catching in a RAG system.

1. Groundedness

The answer should be derived only from the information presented in the context. Catches the most common failure: an answer that draws on the model's general knowledge instead of the documents you uploaded. A high rating means every claim in the answer traces back to something in the retrieved passages.

2. Relevance

How well the answer addresses the main aspects of the question, based on the context. An answer can be perfectly grounded in the documents and still be useless if it answers the wrong question. Relevance checks that the answer covers what was actually asked.

3. Faithfulness

The answer can be directly inferred based on the context. Stricter than groundedness: every statement must be a fair reading of what the documents say, not a creative paraphrase that adds information. Useful for catching subtle hallucinations where a statement is "consistent with" the context but not actually stated there.

4. Context precision

Verify if the context was useful in arriving at the given answer. This judges the retrieval step, not just the generation. If the cited passages are unrelated to the question, a high groundedness score is suspicious — the model may have cherry-picked from irrelevant material.

5. Context recall

Analyze each sentence in the answer and classify if the sentence can be attributed to the given context or not. Sentence-level attribution. A high score means every sentence in the answer has a basis in the retrieved passages; a low score flags unsupported sentences for closer inspection.

Statements that the documents lack something are not scored. When retrieval comes up short, the answer often says so — for example, “The provided documents do not list specific metrics.” A judge left to itself marks that sentence as unsupported, because the context never states its own gaps, and lowers the score for what is an honest answer. Every metric therefore tells the judge to ignore such statements and rate only the rest of the answer. If the answer consists only of such a statement, the judge instead checks that the documents really do lack the requested information.

Why a separate judge model

Self-evaluation has a bias problem. A model asked to grade its own answer has an incentive — not a deliberate one, but a statistical one — to be lenient. Asking a different model removes that pressure and gives the rating more independence from the answer.

The application does not pick a judge model for you. The sidebar has a Judge model dropdown that lists every chat model you have installed locally; you choose one explicitly. If you select the same model that generated the answer, a small caption warns that self-evaluation bias is more likely.

Practical recommendations:

  • Use a model at least as capable as your answer model — a weaker judge cannot reliably critique a stronger answer.
  • Use a different model family when possible. Two models from the same training lineage share blind spots; a different lineage reduces that.
  • Re-run with two judges on the same answer when the rating matters. If both judges agree, the score is robust; if they disagree, look at the explanations, not just the numbers.

The cache key and judge comparison

Every evaluation is stored in session state under a key built from three things: the question, the answer, and the judge model. The key looks like <12-char-hash>__<judge-model>.

The hash part is the same for the same Q&A pair; the judge-model part differs when you change judges. This means a single answer can accumulate several evaluations under different judges, all visible in the export. Switching the dropdown and clicking Run evaluation again does not overwrite the previous one — it produces a new cached entry.

The same Q&A evaluated by two different judges is a built-in way to triangulate. The exported CSV records both, and the HTML report shows a card per judge, so you can see where they agree and where they diverge.

Session-only by design

Evaluations live in the browser session and are cleared when the app restarts. This is deliberate: the cache is intentionally not a research database, and persisting it would create the illusion that older evaluations are still comparable to today's answers after you have changed retrieval settings, models, or even the embedding model.

Three export buttons under 📤 Export evaluations in the sidebar convert the current session's evaluations into a file you control:

CSV (long-form)

One row per metric. Includes the full question and answer text so you can analyze, pivot, or plot the results in a spreadsheet or pandas without needing to recover anything from the chat history.

Markdown

Readable summary grouped by question, with one ratings table per judge model. Suited for pasting into notes, sharing with collaborators, or committing to a repository.

HTML

Standalone Bootstrap document with the question, the answer, and a card per metric per judge. Opens in any browser and prints cleanly.

The export buttons appear only after at least one evaluation has been cached. There is no automatic export — the application never writes evaluation results to disk on its own.

What it costs

Five judge calls per evaluation. On a typical 7B model running on a consumer GPU, expect 30–90 seconds per evaluation; smaller models finish faster but produce noisier scores.

Cached evaluations are free on re-render — if you close and reopen the 🔬 Evaluate this answer expander, the saved report comes back without re-calling the judge.

Caveats specific to small local models

  • Smaller judges (3B–7B parameters) frequently wrap their JSON output in code fences or add prose around it. The evaluator handles this with a three-stage parse fallback — direct parse, fence stripping, regex extraction — and shows the raw output if all three fail.
  • Judge quality drops noticeably below 8B parameters. The default-sized judge model is still yours to choose, but a 13B+ judge produces more stable ratings.
  • Ratings from different judges are not on a shared scale. A "5/5" from one judge may correspond to a "4/5" from another. Compare within a judge, not across them.
